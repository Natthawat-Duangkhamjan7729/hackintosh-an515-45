## 2026-11-06: where the 34 W limit comes from; SSDT-PWRL (update)

DSDT (dump in `acpi-analysis/`): EC query `_Q20` reads EC RAM bytes SUPL (0x8D), SPPT (0x8E), FPPT (0x8F) and TCLT (0x32) from `ECMM` (SystemMemory 0xFE000800) and calls `\CDPC (0x05 STAPM, 0x07 slow PPT, 0x06 fast PPT, 0x03 Tctl)`, which multiplies watts by 1000 and passes them to `\_SB.ALIB (0x0C, ...)` (AMD ALIB, the same path RyzenAdj documents for these limits). So the EC chooses the limits (per power source and probably the NitroSense mode), and the firmware applies them through ALIB in any OS. The AC 34 W and battery 18.5 W levels fit this. The EC values were not read (no EC/physical-memory reader on macOS).
Other macOS options checked: RyzenAdj v0.19.0 (2026-05-13) talks to the SMU through libpci; pciutils' macOS backend uses the AppleACPIPlatformExpert user client, which needs boot-arg `debug=0x144` and root, and limits must be re-applied after the EC changes them. UXTU4Unix wraps RyzenAdj (DirectHW or the same debug=0x144 path) and warns about conflicts with SMCAMDProcessor. Neither documents Tahoe.
